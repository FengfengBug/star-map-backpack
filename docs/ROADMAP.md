## 1. 项目一句话定义

一个把课程笔记变成可编辑知识星图，在用户给定的时间预算和自评掌握度下，用 0-1 背包生成可解释复习航线，并在每次复习后动态重排的学习优先级决策器。

## 2. 产品边界与文案红线

- 不承诺学习效果，不出现“速成”“几小时复习完”“保过”“押题”“期末救命”等话术。
- 统一使用“时间预算下的优先级决策”“可解释取舍”“参数由用户确认”。
- 示例数据必须标注“示例数据，参数可编辑”，不得伪装成真实解析结果；若编辑能力尚未上线，必须同时明确“编辑能力将在后续 Sprint 开放”，不得伪装已可编辑。
- AI 只做辅助：建议拆分知识点（用户确认后才写入）、生成自测题、把算法理由翻译成人话。AI 不得替用户决定分值权重或掌握度。
- 不开发账号系统、后端、云数据库。

## 3. 全局开发守则

1. 严格按 Sprint 顺序执行，不跳 Sprint，不一次性做多个任务卡。
2. 每次执行任务前，先读取 `docs/ROADMAP.md`，用 3–5 行报告：要执行的任务 ID、计划改动、验收方式。若发现任务卡与工作区现状冲突，先停下报告，不要擅自改方向。
3. 每个任务卡完成后必须 `npm run build` 成功；若失败，先修复再报告。
4. 算法必须放在 `src/algorithms/`，纯 TypeScript 函数，不依赖 React，必须有单元测试。
5. 示例数据与真实解析分离：示例数据放 `src/data/`，必须标注“示例数据，参数可编辑”，不得伪装成真实解析结果。
6. 禁止用静态假数据掩盖未实现的功能；未完成的功能要么禁用并标注，要么不展示。
7. UI 遵循深空主题：深蓝黑渐变底（`#070B18` 到 `#101A33`），星星用蓝/青/紫/少量金；信息卡片化；动效 200–300ms 用于卡片、400–600ms 用于航线，缓动 `cubic-bezier(0.22, 1, 0.36, 1)`；移动端优先，星图在窄屏退化为列表航线；避免过度炫光和粒子堆砌。
8. 所有涉及 UI 的任务，必须先完成“静态视觉确认”再接入数据：先给组件/页面静态状态或截图，用户确认后再接业务逻辑。
9. 每个任务卡完成后，在 `docs/ROADMAP.md` 中把该任务标记为“已完成”，并写一行完成说明。
10. 任何对任务卡的增删改，必须写入 Changelog；任何未在当前任务修复的问题，必须写入 Backlog。清单可以变，但必须留痕。
12. 每个开发任务结束时，在回复末尾输出一行“本次任务简要说明：……”。只有我明确说“记录这条”并附截图时，你才把截图存入 `docs/screenshots/`（文件名带日期和任务号），在 `DEVLOG.md` 追加一条（日期、任务名、默认使用你任务结束时那句说明或我另给的说明、图片引用），然后 `git add`、`commit`、`push`。`push` 失败报告并停下，不重试。不要自动记录每个任务。

## 4. Definition of Done（DoD）

每个任务卡完成必须同时满足：

- `npm run build` 成功。
- 任务卡“验收标准”逐条通过。
- 无 P0 问题。
- 涉及 UI 的任务已完成静态视觉确认。
- 相关文档（任务卡状态、Changelog、Backlog）已更新。
- 演示方法可实际走通。
- 未用假数据掩盖未实现功能。

## 5. 问题分级与变更管理规则

### 5.1 问题分级

| 分级 | 定义 | 处理方式 |
| --- | --- | --- |
| P0 阻塞 | 构建失败、核心流程走不通、验收标准过不了。 | 当前任务内立即修复，不新开卡；完成后在任务卡“修复记录”写一行。 |
| P1 体验问题 | UI 不美、交互别扭、文案不清，但功能可运行。 | 记入 Backlog，指定目标 Sprint（如下一 Sprint 的评审窗口或 Task 7.4），不打断当前 Sprint。 |
| P2 优化建议 | 可有可无的优化。 | 记入 Backlog，不承诺时间。 |
| 方向性变更 | 改变产品定位、Sprint 顺序或核心交互。 | 写 Change Request 到 Changelog，必须用户确认后才调整后续任务卡。 |

### 5.2 变更规则

- Sprint 目标保持稳定，任务卡允许受控增补；增补卡编号使用 `Task X.Y-fix` 或 `Task X.99`。
- 每个 Sprint 最后一个任务卡固定为“Sprint Review & Backlog Grooming”，集中处理本 Sprint 的 P1/P2，决定哪些进入下一 Sprint、哪些关闭。
- 初始拆分中的明确例外：Sprint 2、3、4 不单设 `xx.99`，其 P1/P2 统一在 Task 5.99 的 Sprint 2–5 集中评审中处理。除该例外外，任何调整都必须经用户确认并记入 Changelog。
- 单个任务返工不超过 2 轮；超过则降级进 Backlog 或拆成新任务卡。
- 用户提出不满意时，先判定分级，再按上述规则处理，不要每次直接改主线。
- Backlog 每条包含：ID、来源、问题描述、分级、目标 Sprint、状态（待处理/已排期/已关闭）。
- Changelog 每条包含：日期、变更类型（增/删/改/方向变更）、涉及任务卡、原因、影响。

- 同一时间只允许一个任务卡处于“进行中”。
